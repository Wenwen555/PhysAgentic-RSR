## Step 2：添加物理参数可控的仿真环境（摩擦系数）

新建 `capx/envs/simulators/robosuite_physics_lift.py`，继承
`FrankaRobosuiteCubeLiftLowLevel`，新增 `friction` 参数；`_apply_physics()`
把物体 contact geom 的滑动摩擦 `geom_friction[:, 0]` 写为指定值，并在
`reset()` 中调用。已在 `capx/envs/simulators/__init__.py` 注册
`franka_robosuite_physics_lift_low_level`。

### 实现要点 / 踩坑

- **必须在 `super().reset()` 之后再写摩擦**。Robosuite Lift 默认
  `hard_reset=True`，`robosuite_env.reset()` 内部会 `_load_model()` +
  `_initialize_sim()` 重建 `self.model` 与 `self.sim`（新 `mjModel`），
  reset 之前对旧 model 的改动会被丢弃。这一点与直觉相反，先写会被静默覆盖。
- 只修改接触 geom（`geom_contype != 0 or geom_conaffinity != 0`），
  不影响视觉 geom / 外观 / 几何。
- `geom_friction` 不参与编译后的质量矩阵，无需更新模型常量，这也是选择
  摩擦作为第一版的原因（`body_mass` / `body_inertia` 则相反）。
- 摩擦 knobs 仅存在于仿真侧；控制面（`goto_pose`/`open_gripper`/`close_gripper`/
  `sample_grasp_pose`）与 `FrankaRealLowLevel` 完全一致，程序可无缝切真机。
  隐藏物理参数不通过 `info`/observation 暴露。

### 验收结果

`tests/test_robosuite_physics_lift.py` 运行通过：

```
target: 0.2  actual: [0.2]
target: 0.5  actual: [0.5]
target: 1.0  actual: [1.0]
PASS
```

⚠️ 这仅证明参数已写入模型，尚未证明不同摩擦下物体运动/接触力/是否滑落有
行为差异——该验证属于后续步骤（不同摩擦下的运动与抓取差异观察）。

## Step 3：Cube Lift 扩展为长条物体（Rod Lift）

新建 `capx/envs/simulators/robosuite_rod_lift.py`，包含：

- `RodObject(BoxObject)`：长条 box + 一端隐藏配重（sphere geom）。
- `RodLift(Lift)`：重写 `_load_model()` 创建 RodObject，重写成功条件。
- `FrankaRobosuiteRodLiftLowLevel`：低层 wrapper，暴露物理 knobs。
- `rod_mass_properties()`：解析模型（均匀长条 + 点质量配重，平行轴定理），
  供测试校验 MuJoCo 编译结果。

注册名 `franka_robosuite_rod_lift_low_level`。为让子类替换底层 env，
`FrankaRobosuiteCubeLiftLowLevel` 抽出 `_robosuite_env_cls` 类属性与
`_robosuite_env_kwargs()` 钩子（原三处 `Lift(...)` 调用改为
`self._robosuite_env_cls(..., **self._robosuite_env_kwargs())`）。

默认尺寸 (a,b,c)=(0.15,0.015,0.015) 半尺寸 → 0.30×0.03×0.03 m 长条。

### 质量分布自洽模型

配重放在长轴 x 上、距端面 `_COUNTERWEIGHT_INSET` 处，质量由目标 CoM 偏移解出：

```
x_c = (m_b·0 + m_w·x_w)/(m_b+m_w)  →  m_w = m_b·x_c/(x_w−x_c)
I = I_b + m_b(x_b−x_c)² + I_w + m_w(x_w−x_c)²
```

由 MuJoCo 从两个 geom 自动汇总质量/质心/惯量（含平行轴），保证与真实质量分布
对应，而非手改 `body_ipos`。

### 踩坑（MuJoCo 行为）

- **`contype=0` 的 geom 不计入 body 质量/惯量**。最初把配重设成 group=2
  +contype=0，结果 `body_mass` 仍是 0.27（只有长条）。正确做法：配重必须
  `group=0`（碰撞位，才计入质量），但 `conaffinity=0`（永不产生接触），且
  group=0 无视觉位故不可见。代价是它进入 robosuite 的 `contact_geoms` 列表，
  但 conaffinity=0 使 `_check_grasp` 实际不受影响。
- **`body_inertia` 是惯性系（`body_iquat`）下的主惯量对角**。对（部分）对称
  物体 MuJoCo 会选一个置换过的惯性系（本例 `body_iquat=[.5,.5,.5,.5]`），
  因此测试须比较排序后的主惯量，而非逐轴比较。
- 物理校验：`body_mass`=0.4136、`body_ipos`=[0.05,0,0] 与解析模型完全一致；
  排序主惯量 `[4.1e-5, 3.99e-3, 3.99e-3]` 一致（差值来自配重球自身惯量 ~5e-7）。

### 新成功条件（稳定保持，替代瞬时抬升）

`RodLift._check_success()`：物体同时满足 lifted（高于桌面 `lift_threshold`）、
grasped（夹爪接触长条）、level（长轴近水平），连续 `hold_steps` 次判定才算成功。
计数器由 `sim.data.time` 去重（`reward()` 与 `task_completed()` 会各调一次
`_check_success`，同一时刻只计一次）。

### 验收结果

`tests/test_robosuite_rod_lift.py` 通过：尺寸、uniform/com_offset 两种质心下的
质量/质心/惯量自洽、稳定保持计数（连判 3 次成功、一次掉落即清零）。

⚠️ 尚未验证真实抓取下的行为（不同抓取位置/质心偏移导致的滑落差异）——这是
Step 4 候选程序对比要做的。

## Step 4：Direct-CaP vs Sim-CaP 公平对比（M1 Oracle Physics）

新建 `physrsr/`：

| 文件 | 作用 |
|---|---|
| `physics_spec.py` | `PhysicsSpec` / `TestCase` / `CaseResult` |
| `candidate_programs.py` | 候选程序 P1–P6 + `grasp_point()` 沿长轴解析抓取点 |
| `worker.py` | `RolloutWorker`：建 env + API，跑程序，稳定保持判定 |
| `sim_worker.py` / `gt_worker.py` | Simulator（反馈）/ Ground Truth（隐藏评估，独立种子） |
| `run_experiment.py` | 配对协议 + 规则式 Direct/Sim agent + 结果落 JSON |
| `evaluate.py` | 汇总指标 |

配对设计：Direct 与 Sim 对同一物理配置用同一候选池、同一验证种子；只有 Sim
能看到仿真 rollouts。规则式 agent：Direct 选「抓 CoM」（物理推理基线），Sim
选仿真成功率最高的程序。

### 前置依赖：PyRoKi IK 服务

rollouts 走 CaP-X 控制 API（`goto_pose` → PyRoKi IK），必须先启动：

```
python -m capx.serving.launch_pyroki_server --port 8116 --host 127.0.0.1 --robot panda_description --target-link panda_hand
```

否则 `goto_pose` 连接 127.0.0.1:8116 失败。（`init_pyroki` 走远程 HTTP IK。）

### 关键去险发现（影响实验设计）

1. **抓取位置确实影响成败，但机理不是「离 CoM 就滑落」**。Panda 夹爪夹紧力 +
   摩擦足以握住 0.05m 质心偏移的长条（0.41kg、0.2 N·m 扭矩），抓中心直接抬升
   也能成功；真正的失败模式是**夹爪在下压接近时把长条撞倒/推滑**（off-center
   下降路径撞击长条边缘）。
2. 长条在 robot base 系中长轴方向是 `[-1,0,0]`（约 180° z 旋转），因此抓取
   偏移必须由实际四元数计算（`candidate_programs.rod_pose()` 已处理），不能
   假设与 base x 轴对齐。
3. 每个 rollouts 需独立种子：wrapper 的 `reset(seed=...)` 只 seed 自己未用的
   `_rng`，真正控制物体摆放的是 `robosuite_env.rng`，worker 里已显式
   `env.robosuite_env.rng = np.random.default_rng(seed)` 再 reset。

### 首轮运行（2 sim + 2 gt 种子，仅验证 harness）

```
offset_005  direct=P2 sim=P5  direct_gt=0.00 sim_gt=0.00
uniform_000 direct=P2 sim=P3  direct_gt=0.50 sim_gt=0.50
```

候选程序成功率有真实分化（offset_005 下几乎全失败、P5 仿真 0.5；uniform_000
下 P3 仿真 1.0）。harness 端到端跑通、结果落 `outputs/physics_cap/results.json`。

⚠️ M1 是上界验证机制（oracle sim == GT 模型），且 2 种子噪声很大；正式结论
需更多种子 + M2 参数不确定实验。种子少是因为 IK + 硬 reset 使单个 rollout 约
2–3s。

## Step 4.1：M1 harness 加固（更多种子 + 物理参数网格）

首轮只跑 2 个配置 × 2 个种子、且 GT 只评估被选中的两个候选，无法支撑任何
结论。本步把 harness 加固成可重复、可解释的实验：

### 协议变化

1. **物理网格**：`com_offset ∈ {−6,−3,0,+3,+6} cm × friction ∈ {0.2,0.5,1.0}`
   → 15 个 case，每 case 6 个候选。
2. **种子**：sim 8 个（`1..8`，用于选择）× gt 32 个（`1001..1032`，用于
   评估），两者不相交。
3. **GT 全候选评估**：不再只评估被选中的程序，而是 6 个候选全部在 GT 上打分。
   这样才能定义 oracle（GT 最优候选）和每个方法的 **regret**，并让
   sim−direct 可以做**同一 GT 种子上的配对比较**（而不是两组独立样本）。
4. **误差与失败模式分离**：`RolloutRecord.status ∈ {success, fail, error}`，
   `fail` 还带首个违反的稳定保持条件（`not_lifted` / `not_grasped` /
   `not_level`）。原实现把异常直接返回 `False`，IK 服务挂掉时会伪装成「全部
   失败」的合理结果。
5. **并行**：按 (case, candidate, role) 拆成 180 个任务，spawn 进程池 32 路。
   单 rollout ~2.2s，全网格 3600 rollouts 约 5 分钟。
6. **preflight**：正式跑之前校验 (a) 摩擦真的写进了编译后的 `mjModel`，
   (b) rollout 真能执行（IK 服务在线），(c) 同 `(program, seed)` 可复现。
   任一项失败直接 abort。

### 关键踩坑：IK warm-start 让 rollout 不可复现

preflight 第一次就抓到：同一个 `(P1, seed=7)` 连续两次分别得到
`fail/not_lifted` 和 `success`。

根因是 `FrankaControlPrivilegedApi.cfg` —— 它把上一次 IK 解当作下一次的
warm start（`prev_cfg`）。worker 复用同一个 API 对象，于是上一个 rollout 的
末端构型会改变下一个 rollout 的第一个 IK 解，机械臂走不同的路径，撞到长条
的方式也不同。

修复：每次 rollout 开始前 `api.cfg = None`（冷启动 IK）。修复后同
`(P1, seed=7)` 连跑 4 次结果完全一致。

> 这也说明 Step 4 首轮 smoke 结果被跨 rollout 的 warm start 污染了，只能当作
> harness 连通性验证，不能引用。

### 关键踩坑二：物体摆放的 RNG 根本没被 seed 到

修完 warm start 后跑完整网格，发现一个自检信号：`com_offset=0` 时候选 P1
（抓几何中心）和 P2（抓 CoM）在几何上**完全等价**，但 GT 成功率分别是 0.69
和 0.50 —— 同一批种子、同一组程序，结果却不同，说明还有残余随机性。

定位过程：

1. 三个独立进程用同一个 seed reset，读 `cube_poses` 与 `robot0_joint_pos`
   → 位置不同，**不是 IK 的锅**。
2. 读 robosuite 源码：`Robot.reset(deterministic, rng)` 用的是
   `self.rng`（我们已 seed），但 `Lift._reset_internal` 里物体摆放走的是
   `self.placement_initializer.sample()`。
3. 我们的 `RodLift._load_model()` 只在 **首次** 创建 `UniformRandomSampler`，
   之后 hard reset 只调用 `reset()/add_objects()` 复用同一个 sampler。而
   sampler 的 `rng` 是构造时 `MujocoEnv.__init__` 给的
   `np.random.default_rng()`（**OS 熵**）。因此无论怎么 seed `env.rng`，
   摆放都不可复现。

修复：新增 `RodLift.seed_episode(seed)`，同时 seed `self.rng`（机器人初始
噪声）和 `placement_initializer.rng`（物体摆放）；worker 在每次 reset 前调用。
修复后：

- 同进程 / 跨进程 / 并发，同一个 seed 的 reset 状态**逐位相同**；
- `com=0` 时 P1 与 P2 在 8 个种子上结果 8/8 一致（完全等价程序给出完全相同
  结果），这是最有效的自检。

preflight 也因此加强：新增 **reset 状态指纹**（rod pose + 7 个关节角）比对，
比「两次 rollout 成功/失败是否一致」敏感得多——后者太粗，摆放略有差异时
仍可能同样成功。

> 第一轮完整网格（3600 rollouts）是在摆放未 seed 的情况下跑的，**已丢弃**，
> 不作为结果引用。

### 统计口径

- 每个成功率给 Wilson 95% CI（小样本比正态近似可靠）。
- oracle 是**样本内** max（对 6 个带噪估计取最大，偏乐观），因此额外报告
  **split-half oracle**：用一半 GT 种子选候选、另一半打分，两个方向平均，
  作为无偏的「最优可选程序」估计。
- `sim − direct` 用**按 case 聚类、case 内按种子重采样的 bootstrap**（两者在
  同一 GT 种子上配对）。
- 另报 sim 与 GT 的排序一致性（Spearman ρ）和平均成功率误差——这才是 M1
  能回答的问题：仿真反馈是否跟踪真实排序。

### 运行

```
15 cases × 6 candidates × (8 sim + 32 gt seeds) = 3600 rollouts
jobs=32，284s，0 个 error，平均 2.06s/rollout
```

输出：`outputs/physics_cap/results.json`（config + summary + 每 case 行）、
`outputs/physics_cap/rollouts.jsonl`（3600 条逐 rollout 记录）。

### 结果（确定性修复后）

| com_offset | direct_gt | sim_gt | oracle_gt | 选中 (d/s/o) |
|---|---|---|---|---|
| −6 cm | 0.06 | 0.06 | 0.06 | P2/P2/P1 |
| −3 cm | 0.12 | 0.09 | 0.12 | P2/P1/P2 |
|  0 cm | 0.44 | 0.53 | 0.53 | P2/P3/P3 |
| +3 cm | 0.19 | 0.19 | 0.19 | P2/P2/P2 |
| +6 cm | 0.06 | 0.06 | 0.06 | P2/P2/P1 |

（每个 com 下 3 个摩擦值结果**完全相同**，故合并；见下。）

汇总：

```
mean GT success   direct=0.175  sim=0.188  oracle=0.194
oracle (split-half, 无偏) = 0.175
mean regret       direct=0.019  sim=0.006
paired sim-direct +0.013  95% CI [-0.013, +0.042]   （不显著）
sim picks oracle  6/15    direct picks oracle 6/15
sim-vs-GT         |rate error|=0.064   Spearman rho=0.634
```

### 三条结论（以及它们对 M2 的影响）

1. **harness 现在是确定性的，而且能被内部一致性自检证明**。
   `com=0` 时 P1（抓中心）与 P2（抓 CoM）几何上完全等价，它们在 32 个 GT
   种子上**逐种子完全相同**（三个摩擦值下都成立）。这比 preflight 的两次
   重复更强——任何残余随机性都会让这两个程序的逐种子结果错开。

2. **摩擦轴在本任务中完全无效**。把 `(program, seed)` 固定，μ ∈ {0.2,0.5,1.0}
   的 1080 组结果**逐条完全相同**（`0/1080` 有差异）。原因是失败模式由
   几何/运动学决定（夹爪下压时把长条撞倒），而抓取成功时夹紧力远大于所需
   摩擦力，从不发生滑移。**因此这 2/3 的计算是浪费的**：M1 的摩擦维度应删除；
   M2 若要研究摩擦，需要让任务对摩擦敏感（更重/更滑的物体、或加入推/滑阶段），
   否则估出来的 μ 对决策没有任何因果作用。

3. **选择方法之间没有可测差异，但这不是 UI 问题，而是候选池的天花板问题**。
   仿真反馈确实跟踪真实排序（ρ=0.634、平均率误差 0.064），可是 oracle 只有
   0.194（split-half 无偏估计 0.175），也就是**即使完美选到池内最优程序也只有
   ~19% 成功率**。留给「选择得更好」的空间最多 0.019，sim−direct 的
   +0.013 完全淹没在噪声里。M2 之前必须先解决这个：提高候选程序质量
   （更好的接近/抓取策略）或降低任务难度，让 oracle 有足够抬头空间，否则
   Direct vs Sim 的比较不可证伪。

### 附带发现

- 失败模式（3600 rollouts，87.4% 失败）：`not_lifted` 占大头（夹爪没夹起来），
  `not_level` 其次（抬起后长条倾斜），`not_grasped` 很少。P5/P6（抓两端）
  几乎必失败，说明当前接近路径对偏心抓取很不友好。
- 每个 case 32 个 GT 种子的 Wilson CI 约 ±0.15（0.5 附近），单 case 的数值
  只能看趋势；跨 15 个 case 聚合后才谈得上比较。





## Step 4.2（阶段 A）：修正长条任务，让物理效应真正发生

Step 4.1 的结论很刺眼：即使 oracle 也只有 0.19 成功率，而且 **摩擦轴完全
无效**（1080 组结果逐条相同）。一个「抓几何中心」的基础程序在正常物理条件下
只有 44% 成功率，说明失败根本不是物理（CoM / 摩擦）造成的，而是抓取管线本身
有问题——必须先修好，否则后续关于物理参数的实验测的都是管线缺陷。

### 阶段标识（per-phase instrumentation）

原先只记录首个被违反的稳定保持条件（`not_lifted` / `not_grasped` /
`not_level`），它说明「什么坏了」但不说「坏在哪」。新增
`physrsr/phase_tracker.py`，把程序按经典抓取管线切成 5 段：

| 阶段 | 应建立的状态 | 该阶段大量失败说明 |
|---|---|---|
| `pre_grasp` | 到达预抓取位姿且不扰动物体 | IK / 控制器精度、接近轨迹碰撞 |
| `contact` | 两个指垫同时接触物体（有效抓取） | 抓取几何 / 接触构型 |
| `lift` | 物体离开桌面，且离开时不倾转 | CoM、夹持力、摩擦 |
| `transport` | 搬运中保持已抓取 + 抬起 + 水平 | 惯量、加速度、接触 |
| `placement` | 稳定落位 | 支撑、接触动力学（本任务不用） |

实现要点：

- 阶段切分只依据**控制 API 调用**（`goto_pose` / `open_gripper` /
  `close_gripper`），所以同一份代码在真机上含义完全一致；状态采样通过
  `state_fn` 注入——仿真里读特权状态（`body_xpos`、手指 qpos、接触对），
  真机上换成夹爪宽度 / 力/接触传感 / 物体跟踪，接口不变（AGENTS.md）。
- 每条 `RolloutRecord` 现在带 `failure_phase`、`grasp_established`（两个指垫
  是否都真的碰到物体）和完整 `phases` 样本（含 `commanded`、`achieved`、
  `tcp_error`、`finger_width`、`rod_tilt` 等）。
- `attribute_failure()` 归因规则：抓取前就被扰动 → `pre_grasp`；没有有效抓取
  → `contact`；抬起失败，或**抬起动作结束时已倾斜** → `lift`；抬起来之后才
  丢失/倾转 → `transport`。
- `evaluate.py` 的汇总新增失败阶段分布、按程序的有效抓取率、接近段
  `|commanded − achieved|` 误差统计。

### 查到的三个真 bug（外加两个控制精度问题）

1. **物体姿态四元数的 x/y/z/w 顺序搞错**（最致命）。
   robosuite 的 `Lift._get_observations()` 里 `cube_quat` 是
   `convert_quat(..., to="xyzw")`，而 `_cube_pose_dict()` 把它当 wxyz 喂给
   `vtf.SE3`。立方体是偏航对称的，所以这个 bug 一直没人发现；长条不是——程序
   以为长条沿世界 x 轴，实际偏航 67.6°，于是「对准长条短边」的夹爪实际是斜着
   压上去，夹住长条的顶棱而不是两侧。这正是「抓着抓着就掉了」的根源。
   修复：`_cube_pose_dict()`（cube_lift / cubes / cubes_restack）先转成 wxyz。

2. **物体位姿用的基准体和 IK 用的基准体不是同一个**。
   `base_link_idx` 取的是 `fixed_mount0_base`（world z = 0.922），而 IK 求解器
   与 `get_eef_pose()` 用的是 `robot0_base`（z = 0.912），差 1 cm。程序把观测
   位置直接当 IK 目标，于是系统性在地下压 1 cm。
   修复：`base_link_idx` 改为 `robot0_base`。

3. **reset 之后观测是陈旧的**。物体在桌面上方 1 cm 处生成，wrapper 的 settle
   循环直接调 `sim.step()`，不会刷新 robosuite 的 observable 缓存，所以程序
   在 reset 后立刻读到的还是**生成位置**（高 1 cm）。抓取点因此整体偏高 1 cm。
   修复：settle 之后 `_update_observables(force=True)`。

另外两个精度问题（阶段 A 之前已定位，这里一并记录）：

4. **IK 在收缩过的关节限位上卡住**：IK 服务用
   `set_min_distance_from_limits(urdf, 0.15)` 建模型，冷启动从全零解起会贴到
   限位上，留下 1–2 cm 位置残差。修复：服务端新增可选的确定性多起点
   （`num_starts`，默认 1 保持旧行为），特权 API 请求 8 起点。
5. **关节空间稳态误差 + hand→TCP 约定误差**：`JOINT_POSITION` 控制器有
   ~0.0148 rad 稳态误差，加上 IK 模型里 hand→TCP 的偏移和仿真差 ~1 cm，
   开环下末端会短 1.5–1.9 cm。修复：`_solve_and_move()` 闭环保底——每轮读
   `get_eef_pose()`（仿真读 `gripper0_right_eef`，真机读关节编码器 FK），把
   残差补到 IK 目标上重解，3 轮内收敛到 3 mm。

### 结果

修复后（`com_offset=0`，`friction=1.0`，`hold_steps=10`）：

| 程序 | 抓取位置 | 20 种子成功率 | 有效抓取率 |
|---|---|---|---|
| P1 | 几何中心，直接抬 | **1.00** | 1.00 |
| P2 | CoM，直接抬 | **1.00** | 1.00 |
| P3 | CoM，小步抬 | **1.00** | 1.00 |
| P4 | 中心，小步抬 | **1.00** | 1.00 |
| P5 | 左端（−10.5 cm），直接抬 | **1.00** | 1.00 |
| P6 | 右端（+10.5 cm），直接抬 | **1.00** | 1.00 |

- P1 单独扩到 60 个种子（1001–1060）仍是 **60/60**；同 seed 重复逐位一致。
- 接近段 `|commanded − achieved|`：mean 1.6 mm，p95 4.3 mm，max 5.4 mm
  （之前是 15–40 mm）。
- 注意现在**所有程序都 100%**，因为中心 CoM 下没有物理难度——这正是阶段 A
  的目标（先让基础程序可靠），物理区分度要靠下一步加大难度得到。

### 物理效应验证（`com_offset = +10 cm`）

| 程序 | 成功率 | 失败阶段 | 说明 |
|---|---|---|---|
| P1 / P4（抓中心） | 0.00 | `lift` | 有效抓取 1.00，抬离桌面时即倾转 |
| P5（抓 −10.5 cm 一端） | 0.00 | `lift` | CoM 在远端，力矩最大 |
| P2 / P3（抓 CoM） | 1.00 | — | 力矩为零 |
| P6（抓 +10.5 cm 一端） | 1.00 | — | 恰好就在 CoM 上 |

失败全部被归因到 `lift`（而不是 `contact`），且 `grasp_established` 均为真，
说明管线是通的、坏的是物理——CoM 力矩在物体离桌瞬间就让它倾转。至此
「抓取几何」与「物理效应」终于分离开了。

### 下一步

按阶段 A 的路线继续加难度：运动速度（`goto_pose` 的步长/速度）、接触难度
（更低的摩擦、更小的指垫接触面积），并让摩擦重新变成有效变量——Step 4.1
里摩擦无效是因为失败发生在抓取几何而非滑移；现在几何修好了，需要确认在
`com` 接近抓取点、只差夹持力时，μ 才会真正起作用。

## Step 4.3（阶段 A 续）：运动速度与接触难度

阶段 A 的第三步、第四步：把「运动速度」和「接触难度」做成真正有效的物理变量。
质心偏移已在 Step 4.2 验证有效（`com=+10 cm` 时抓中心 0/6、抓 CoM 6/6，失败
归因 `lift`）。

### 1. 运动速度轴：`goto_pose(..., speed=...)`

实现分两层，保证同一段程序在仿真和真机上行为一致（AGENTS.md 要求）：

- 低层 `move_to_joints_blocking(..., max_joint_speed=...)`
  （[robosuite_base.py](../src/cap-x/capx/envs/simulators/robosuite_base.py)、
  [franka_real.py](../src/cap-x/capx/envs/simulators/franka_real.py)）。
  仿真里按控制步长限制**指令关节**的逐帧增量；真机上按发布周期（0.02 s）
  从**实测关节**向目标步进，只发布不会让电机跳变的中间设定点。两端都会
  自动放宽 `max_steps`，避免慢速移动被**截断**——截断会被误判成物理失败。
- 上层 `goto_pose(position, quat, z_approach=..., speed=...)`：
  `speed ∈ (0, 1]` 是控制器最大关节速度的分数（参考 2.5 rad/s，实测峰值），
  `None` 或 `>= 1` 表示不限速。**不限速时代码路径与旧实现逐位一致**，所以历史
  结果不受影响。慢速分支由单元测试守住：峰值关节速度必须显著下降，且终点
  收敛到同一关节目标。

  说明：真机分支（限速发布中间设定点）尚未在硬件上验证；仿真分支已纳入单元
  测试。两者语义一致（指令关节速度不超过 `max_joint_speed`），差别只在量化
  步长（控制周期 vs 0.02 s 发布周期）。

**速度确实改变结果（μ=1.0，抓几何中心 P1，种子 1001/1003/1005/1007）**：

| `speed` | 成功率 | 说明 |
|---|---|---|
| `None`（全速） | 0/4 | |
| 0.7 | 2/4 | |
| 0.5 | 2/4 | |
| 0.35 | 4/4 | |
| 0.15 | 4/4 | |

单调关系说明边界上的失败由**惯性**贡献，不只是静力矩。修正接触模型之后
（见下一节，指垫摩擦不再被 `max` 规则吃掉），速度敏感性只出现在**静力边界
附近**的工况：

| 工况 | 全速 P1 | 慢速 P7（speed=0.35） |
|---|---|---|
| μ=2.0, com=+9 cm | 0/6 | **6/6** |
| μ=0.8, 弱夹持 2 N | 5/6 | **6/6** |
| μ=0.7, 弱夹持 2 N | 1/6 | **6/6** |
| μ=0.6, 弱夹持 2 N | 1/6 | 1/6 |

结论：速度不是一个全局难度旋钮，而是**在物理边界附近才起作用**的决策变量。
这正好是 Sim-CaP 应该能发现、Direct-CaP 只能靠先验猜的东西。

### 2. 接触难度：摩擦系数为什么一直无效（两个独立的根因）

之前记录过「μ ∈ {0.15, 0.35, 1.0} 结果完全相同」。这次查清是**两个**原因叠加：

1. **μ 根本没进入接触**。MuJoCo 对两个 geom 的接触参数按**逐元素最大值**
   混合，而 robosuite 的指垫 geom 声明 `friction = 2.0`。杆的 μ 再低，
   接触摩擦仍然是 2.0。诊断脚本直接打印了接触摩擦与两个 geom 的声明值。
   修复：`RodObject` 的碰撞 geom 设 `priority=1`，让物体表面主导自己的接触
   ——对「光滑杆压在橡胶指垫上」这是物理上更正确的建模
   （[robosuite_rod_lift.py](../src/cap-x/capx/envs/simulators/robosuite_rod_lift.py)）。
2. **即使 μ 进了接触，夹持力仍远大于摩擦极限**。Panda 编译的指力上限是
   ±20 N，对 0.27 kg 的杆有 >10 倍余量。新增 `grip_force`（每指力上限）作为
   接触难度旋钮，在 `_reset_internal` 里重新施加（`hard_reset=True` 会重建
   模型，单元测试守住这条）。

**双向验证（com=0，抓中心 P1）**：

| `grip_force` | μ=1.0 | μ=0.5 | μ=0.3 |
|---|---|---|---|
| 机器人默认（20 N） | **3/3** | **3/3** | **3/3** |
| 2 N（弱夹持） | **3/3** | 0/3 | 0/3 |

扩展种子矩阵（7 种子）：默认夹持下全部 7/7；2 N 夹持下 μ=1.0 为 7/7，
μ=0.5 与 μ=0.3 为 0/7，失败全部归因 `lift`（有效抓取 `grasp_established=True`，
是夹持后滑落，不是没抓到）。至此 μ 第一次成为可观测变量——这是 Step 5
（估计 θ=[x_CoM, I, μ]）的前提。

### 3. 修好接触模型后，CoM 边界移动了

物体表面主导接触后，等效摩擦从「指垫 2.0」降到「杆自身的 μ」，力矩容量
减半，静力边界从 |com|≈0.08–0.10 下移到 ≈0.065：

| com | P1（抓中心，全速） | P2（抓 CoM） |
|---|---|---|
| 0.00 | 7/7 | 7/7 |
| 0.06 | 8/8 | 8/8 |
| 0.07 | 0/8（全 `lift`） | 8/8 |
| 0.08 | 0/8 | 8/8 |
| 0.09 | 0/8 | 8/8 |
| 0.12 | 0/7 | 7/7 |

边界很陡（0.06 → 0.07 之间翻转），说明它能干净地区分「抓取几何正确与否」，
而不是靠噪声碰运气。

### 4. 因此 M1 的物理网格改成三条轴

`DEFAULT_COM_OFFSETS = (-0.09, -0.03, 0.0, 0.03, 0.09)`、
`DEFAULT_FRICTIONS = (0.7, 2.0)`、`DEFAULT_GRIP_FORCES = (None, 2.0)`，
共 20 个 case。选择依据是**实测的有效区间**而不是先验：`±0.09` 跨过 CoM 边界；
`μ=2.0` 给出速度敏感的高摩擦工况；`μ=0.7 + 2 N` 给出摩擦敏感工况；
`None`（机器人默认夹持）+ 高 μ 作为「μ 无效」的对照。
候选池同时加入 P7/P8（与 P1/P2 完全相同、只是 `speed=0.35` 的慢速版本），
所以「慢一点」成为一个 agent 可以选择、也可以被仿真否决的程序决策。

### 5. M1 重跑结果（修正后的完整管线）

网格：`com ∈ {-9, -3, 0, 3, 9} cm` × `μ ∈ {0.7, 2.0}` × `grip ∈ {机器人默认, 2 N}`
= 20 个 case；候选池 P1–P8（P7/P8 与 P1/P2 抓取点相同、只是 `speed=0.35`）；
每 case 8 个 sim 种子 + 32 个 gt 种子，共 6400 次 rollout，28 进程约 12 分钟。

| 指标 | 修正前（Step 4.1） | 修正后 |
|---|---|---|
| oracle 上限（gt 平均成功率） | 0.19 | **0.777**（可行 case：**0.971**） |
| 有效抓取率 | — | **0.996** |
| 失败阶段分布 | 基本全是 `transport`（归因错误） | `lift` 3276 / `contact` 28 / `transport` 9 |

20 个 case 的配对对比：

| 指标 | Direct-CaP | Sim-CaP |
|---|---|---|
| 平均 gt 成功率 | 0.653 | **0.762** |
| 平均 regret（相对 in-sample oracle） | 0.123 | **0.014** |
| 选中 oracle 的 case 数 | 4/20 | **18/20** |
| 配对差（sim − direct） | — | **+0.109，95% CI [+0.002, +0.236]** |

排除 4 个「所有候选都不可行」的 case（弱夹持 2 N + μ=0.7 + 任意非零 CoM：
夹持摩擦极限约 2.8 N 仅略高于杆重 2.65 N，任何偏心力矩都会滑落）后：
direct 0.816、sim 0.953、oracle 0.971，配对差 **+0.137 [+0.002, +0.297]**。

仿真对真值的预测能力（M1 里 sim 就是 gt 模型，这是天花板校验）：
逐候选成功率的平均绝对误差 **0.017**，平均 Spearman ρ **0.955**。

**Sim-CaP 的全部收益来自速度轴**，四条 case 全部是「慢一点才行」：

| case | Direct（选 P2，快速抓 CoM） | Sim（选慢速程序） | oracle |
|---|---|---|---|
| com=+9 cm, μ=2.0, 2 N | P2 → 0.00 | **P8 → 0.88** | P8 0.88 |
| com=−9 cm, μ=2.0, 2 N | P2 → 0.00 | **P8 → 0.72** | P8 0.72 |
| com=0, μ=0.7, 2 N | P2 → 0.44 | **P7 → 1.00** | P7 1.00 |
| com=+3 cm, μ=2.0, 2 N | P2 → 0.91 | **P8 → 0.94** | P8 0.94 |

这正是 M1 想验证的东西：**知道 CoM 的规则型 agent 选不出正确程序，因为决定
成败的是惯性/滑移这类只有仿真才能暴露的效应**。同时说明为什么阶段 A 的四条
难度轴值得做——没有速度和接触难度，所有候选在所有 case 上都 100%，Direct 与
Sim 不可能有差别。

### 6. 结论与遗留问题

1. 三条难度轴都已被**实测**证明有效，且各有明确的有效区间：
   CoM（>6.5 cm 时抓中心必失败）、速度（仅在静力/摩擦边界附近起作用）、
   摩擦（仅在弱夹持时起作用）。摩擦在机器人默认 20 N 夹持下仍然无效，
   这是物理事实，不是建模 bug——写进结论，不要硬调。
2. 失败归因现在可用：6400 次 rollout 里 99.6% 建立了有效抓取，`contact`
   类失败只有 28 次（0.4%），说明抓取几何管线已稳定。
3. **4 个不可行 case** 是负对照：证明弱夹持 + 低摩擦下任务本身超出夹爪能力，
   而不是程序不好。保留它们会让 oracle 上限偏低（0.777 vs 0.971），所以报告
   时两种口径都要给。
4. M1 的 sim 就是 gt 模型，所以「Sim 更强」只说明管线正确、上限存在；
   真正的检验在 M2（去掉真值参数 + Active Probe 估计 θ）。
5. 下一步（M2）必须先解决参数可辨识性：现在只有 `com` 与 `grip/mu` 两个方向
   能被单一 rollout 区分，`I` 与 `μ` 需要**主动探索动作**（推/倾斜/快速抬）
   才能分离——这正好对应计划里的 Active Probe。
